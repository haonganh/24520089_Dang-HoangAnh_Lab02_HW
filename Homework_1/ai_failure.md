## 1. Purpose and Audit Boundaries

This file records weaknesses, potential bugs, accessibility risks, incorrect assumptions, and verification gaps in the code previously generated by the AI assistant. It also proposes corrective actions and repeatable checks. The goal is transparent error reporting, not to claim that a passing build or an automated Lighthouse score alone proves accessibility.

**Evidence reviewed:** The assignment screenshot, `ai_rule.md`, `task_decomposition.md`, and source code shown in the conversation for T01–T09 (particularly the latest T08 `DataGrid.tsx` and T09 CSS).  
**Not inspected:** The student's actual current GitHub repository, local files after copying/editing, runtime DOM, package-lock, test outputs, browser console, Lighthouse report, or NVDA results.  
**Consequences:** A finding marked **Confirmed (source)** means the weakness is visible in the generated code. It does **not** mean the failure has been reproduced against the current student repository. Findings marked **Potential** or **Unverified** require the corresponding tests. No claim of verified 100/100 Lighthouse scores or complete WCAG 2.2 AA compliance is made here.

## 4. Recommended Corrections

### AF-001 + AF-003: Stable record identity (P1)

**Why:** Object reference identity and numeric array indices are not reliable identifiers when data is fetched, reconstructed, inserted, or deleted. For the sample `Employee` dataset, `id: number` already exists and is suitable.

**Safe implementation direction:** In the employee-specific demo, use `Employee.id` for React row keys and selected ID membership. For a truly generic reusable `DataGrid<T>`, the required `DataGridProps<T>` contract supplies no guaranteed unique key; document an explicit identity policy. If a public optional `getRowId` prop is proposed, obtain instructor approval before changing the exact prescribed interface. A generic fallback based on array index does **not** resolve identity across replacements.

**Suggested behavioral test:** Select employee ID 11; create a new array with new objects that have the same IDs; re-render; confirm employee ID 11 stays selected and the selection count remains correct. Then insert another employee ahead of ID 11 and verify React does not associate the selected state with the wrong row.

**Acceptance:** Selection and callbacks refer to the correct logical record before and after sorting, filtering, pagination, replacement, insertion, and removal.

### AF-002: Focus management across updates (P1)

**Why:** Grid navigation uses React state, DOM refs, and a `gridHasFocus` ref. Replacing/removing the focused cell can alter the browser's `activeElement` before the layout effect runs.

**Safe implementation direction:** Identify the active cell by a stable logical record ID and column key. Before an update can remove the active row, remember whether focus was inside the grid. After the update, restore focus to the same visible logical cell; if it is gone, use a consistent fallback (for example, the nearest visible cell or active header). Do not steal focus from the search input or pagination control when those initiated the change. Avoid reliance on detached DOM nodes or stale ref arrays.

**Suggested tests:**

1. Focus a body cell using arrow keys, then change `data` externally so that its row disappears. Focus must stay on a sensible visible control and not fall to the page body.
2. While the search input is focused, type a query that eliminates the current body row. Focus must **remain in the input**.
3. Use the keyboard to sort and then navigate the new first page. Exactly one grid navigation target should have `tabIndex=0`.
4. Switch pages using pagination buttons and verify focus stays on the activated button or follows a deliberately documented behavior.

**Acceptance:** No lost focus, hidden focus, unexpected jump, or keyboard trap.

## 5. Observations That Are *Not* Confirmed Bugs

- **TypeScript contract:** The supplied `ColumnDef<T>` and `DataGridProps<T>` definitions match the screenshot and should not be changed casually.
- **Native table semantics:** The latest generated JSX uses a real table and real buttons; this is consistent with the assignment's no-`div`-soup requirement.
- **ARIA sorting and selection:** The latest code attaches `aria-sort` to the active column header and `aria-selected` to each row. Screen-reader effectiveness remains unverified.
- **Basic keyboard behavior:** The code handles all four arrow keys plus Enter/Space for body cells, but browser execution and screen-reader behavior are unverified.
- **Color contrast spot check:** Calculations from the T09 CSS show approximately `10.36:1` for white header text on `#1e3a8a`, `17.06:1` for body text `#0f172a` on `#f8fafc`, and `8.30:1` for selected-label text `#14532d` on `#dcfce7`. These combinations exceed the 4.5:1 ordinary-text target. This is **not** an exhaustive audit of every visual state.
- **Horizontal scrolling of actual tabular content** can be consistent with WCAG 1.4.10's two-dimensional-layout exception, provided no information or functionality is lost.
- **Using `aria-disabled` on pagination controls** is not inherently invalid when behavior is correctly guarded; AF-009 is a usability improvement to consider, not a guaranteed conformance failure.
